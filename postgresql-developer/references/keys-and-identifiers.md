# Keys and Identifiers

Every table gets a primary key. The interesting questions are what it is made of and how it is generated, and the answers have measurable consequences for index size, write throughput and replication.

## Every table, including the ones that feel exempt

Event tables, log tables and append-only tables are routinely created without a primary key on the grounds that nothing looks it up by identity. Add one anyway:

- Logical replication cannot replicate `UPDATE` or `DELETE` on a table with no replica identity, and the default replica identity is the primary key. Without one, you must set `REPLICA IDENTITY FULL`, which makes every update ship the entire old row.
- Deleting a specific bad row without a key means matching on every column and hoping it is unique.
- Many tools - migration frameworks, CDC, ORMs, admin UIs - simply require one.

For a junction table the key is the pair of foreign keys. For an event table `bigint GENERATED ALWAYS AS IDENTITY` costs 8 bytes and an index.

## Surrogate or natural

A **natural key** is data that already identifies the row (an ISBN, a VAT number, an ISO country code). A **surrogate key** is a meaningless value generated for the purpose.

**Default to a surrogate key**, and put a `UNIQUE` constraint on the natural key alongside it.

The argument is not aesthetic. Natural keys fail in a specific, repeated way: the business changes its mind about what identifies a thing. An email address becomes changeable. A "unique" supplier reference turns out to be reused after seven years. A national insurance number turns out to be duplicated in the source system. When that happens with a natural primary key, the change cascades into every referencing table.

Natural keys are correct in two cases:

- **Immutable external standards**: `country_code char(2)`, `currency_code char(3)`. These are defined by a standards body and will not be renumbered.
- **Pure junction tables**: `PRIMARY KEY (order_id, product_id)` is right, and adding a surrogate `id` to a junction table is a common and pointless habit that permits duplicate pairs unless you also add the unique constraint you were avoiding.

Always constrain the natural key even when it is not the primary key. A surrogate key without a `UNIQUE` on the business identifier means duplicate customers, and no error.

## `bigint` identity, the default

```sql
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
```

`GENERATED ALWAYS` rejects an explicit value unless the caller writes `OVERRIDING SYSTEM VALUE`. `GENERATED BY DEFAULT` lets an explicit value through. Prefer `ALWAYS`: it catches the application accidentally supplying an id, and data-loading tools that legitimately need to supply one can say so explicitly.

Why `bigint` rather than `integer`: `integer` exhausts at 2,147,483,647. Reaching it is not rare - a high-volume event table gets there in months - and the fix is a table rewrite plus every referencing foreign key, under an `ACCESS EXCLUSIVE` lock. The 4 extra bytes per row are not worth the risk.

**Sequences have gaps, and that is correct.** A rolled-back transaction, a crash, or a cached block of values all leave gaps. Sequences are non-transactional by design, because making them transactional would serialise every insert. Do not try to make identifiers consecutive - if the business needs a gapless sequence (invoice numbers in some jurisdictions), that is a separate, deliberately serialised counter, not the primary key.

## UUIDs

Use a UUID when identifiers must be generated **outside** the database: by clients, by multiple regions writing independently, or before the row is inserted so that a graph of objects can be assembled in memory. Also when the identifier is exposed publicly and a sequential integer would leak volume (a competitor counting your order numbers).

The version matters enormously.

### UUIDv4 and B-tree locality

`gen_random_uuid()` produces UUIDv4 - 122 random bits. As a primary key, that is a performance problem:

- Inserts land at **random positions** in the B-tree. With sequential keys, inserts concentrate on the rightmost leaf page, which stays in cache. With random keys, every insert dirties a different page, so the working set becomes the whole index rather than its right-hand edge.
- Once the index exceeds available cache, each insert costs a random read plus a random write.
- Page splits happen in the middle of pages rather than at the end, leaving pages around 50% full instead of nearly full. The index is roughly twice the size it needs to be.
- WAL volume rises, because more distinct pages are dirtied per transaction.

### UUIDv7, which fixes it

UUIDv7 puts a 48-bit Unix millisecond timestamp in the high bits, so values generated close in time sort close together. Inserts regain the append-at-the-right-hand-edge behaviour of a sequence while keeping client-side generation and global uniqueness.

```sql
id uuid PRIMARY KEY DEFAULT uuidv7()     -- PostgreSQL 18+
```

On 17 and earlier, generate UUIDv7 in the application - every major language has a library - or use the `pg_uuidv7` extension. Do not fall back to `gen_random_uuid()` for a high-insert-rate table just because `uuidv7()` is unavailable.

The trade-off to state: UUIDv7 leaks creation time. If the identifier is public and creation time is sensitive, that matters. For most systems it does not, and the sortability is a bonus.

### Size

`uuid` is 16 bytes; `bigint` is 8. That doubling propagates into every index and every foreign key column. On a table with five indexes and 500 million rows it is real. It is not, by itself, a reason to avoid UUIDs - but store them as `uuid`, never as `text`, which is 37 bytes and loses all the operators.

### The comparison

| | `bigint` identity | UUIDv4 | UUIDv7 |
|---|---|---|---|
| Size | 8 bytes | 16 bytes | 16 bytes |
| Generated by | Database only | Anywhere | Anywhere |
| Insert locality | Excellent | Poor | Good |
| Index bloat | Low | High | Low |
| Leaks row count | Yes | No | No |
| Leaks creation time | Roughly | No | Yes |
| Human-usable | Yes | No | No |
| Merging datasets | Collides | Safe | Safe |

**Default to `bigint` identity.** Move to UUIDv7 when client-side generation or multi-region writes are a genuine requirement. Choose UUIDv4 only when creation time must not be inferable and you accept the write cost.

### Public identifiers

A common and good pattern is both: a `bigint` primary key for internal joins and foreign keys, plus a separate public identifier column with a unique index.

```sql
CREATE TABLE orders (
    id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    public_id  uuid   NOT NULL DEFAULT uuidv7(),
    reference  text   NOT NULL,       -- human-quotable, e.g. 'ORD-2026-004821'
    CONSTRAINT orders_public_id_key UNIQUE (public_id),
    CONSTRAINT orders_reference_key UNIQUE (reference)
);
```

Joins stay 8 bytes wide, the API never exposes a sequential integer, and support staff have something to read over the phone. The cost is two extra unique indexes.

## Composite keys

A composite primary key is correct for junction tables and for partitioned tables where the partition key must be part of every unique constraint.

```sql
PRIMARY KEY (order_id, line_no)
```

Column order in a composite key matters, because the key creates a B-tree index and that index follows the leftmost-prefix rule. Put the column you filter by most often first. See [composite-and-covering-indexes.md](composite-and-covering-indexes.md).

The cost of composite keys is that every referencing table must carry every column, which is why deep hierarchies with composite keys become unwieldy. In a multi-tenant shared schema this cost is worth paying for the top level, because `FOREIGN KEY (tenant_id, x) REFERENCES t (tenant_id, id)` is what makes cross-tenant references structurally impossible. See [multi-tenancy.md](multi-tenancy.md).

## Foreign keys and their indexes

**PostgreSQL creates an index for a primary key and for a unique constraint. It does not create one for a foreign key.** This is the most commonly missed index in any schema.

```sql
ALTER TABLE orders ADD CONSTRAINT orders_customer_id_fkey
    FOREIGN KEY (customer_id) REFERENCES customers (id);

CREATE INDEX orders_customer_id_idx ON orders (customer_id);   -- you must add this
```

Two things break without it:

1. Joining from the parent to the child is a sequential scan.
2. **Deleting or updating a parent row scans the whole child table** to check for references, while holding a lock. On a large child table this turns a single-row delete into a multi-second, lock-holding operation.

Find them all. This query is verified against PostgreSQL 18:

```sql
SELECT c.conrelid::regclass AS table_name,
       c.conname,
       (SELECT string_agg(a.attname, ', ' ORDER BY k.ord)
        FROM   unnest(c.conkey) WITH ORDINALITY AS k(attnum, ord)
        JOIN   pg_attribute a ON a.attrelid = c.conrelid AND a.attnum = k.attnum
       ) AS columns
FROM   pg_constraint c
WHERE  c.contype = 'f'
AND    c.conrelid IN (SELECT oid FROM pg_class WHERE relkind IN ('r','p'))
AND    NOT EXISTS (
         SELECT 1 FROM pg_index i
         WHERE  i.indrelid = c.conrelid
         AND    i.indisvalid AND i.indislive
         AND    (i.indkey::smallint[])[0:array_length(c.conkey, 1) - 1] @> c.conkey
       )
ORDER  BY 1, 2;
```

Two details in that query that are easy to get wrong:

- **`indkey::smallint[]` is 0-based**, unlike an ordinary PostgreSQL array. `[0:n-1]` therefore takes the first `n` columns. A slice re-bases the result to 1, which matters if you compare two of them - see [index-maintenance.md](index-maintenance.md).
- **`@>` rather than a positional comparison is deliberate.** A foreign key check is equality on every column, so an index on `(b, a)` serves a key on `(a, b)` perfectly well. Order-insensitive containment is the correct semantics here, and a prefix comparison would produce false positives.

Aggregating the column names in a subquery keeps a multi-column foreign key to one row. Joining `unnest` in the outer query reports the same constraint once per column.

The exception is a child table that is small and never has its parent deleted - a lookup table's referencing side. Even then the index is usually cheaper than the reasoning.

## Version notes

- **18** - `uuidv7()` and `uuidv4()` built in. Before 18, generate UUIDv7 in the application or use the `pg_uuidv7` extension.
- **13+** - `gen_random_uuid()` is built in. Before that it required `pgcrypto`.
- **10+** - `GENERATED ALWAYS AS IDENTITY`. Every supported version has it, so `serial` has no remaining justification.
- **18** - identity columns can be added to a partitioned table's parent more flexibly than before.

Sequence gap behaviour, the absence of automatic foreign-key indexes, and B-tree insert locality are identical across 14 to 18.

## Gotchas

- Agent omits a primary key from an event or log table - logical replication cannot replicate updates or deletes without one
- Agent uses `serial` instead of `GENERATED ALWAYS AS IDENTITY` - superseded since PostgreSQL 10, with awkward sequence ownership
- Agent uses `integer` for a surrogate key - 2.1 billion arrives and the fix rewrites the table and every referencing key
- Agent uses `gen_random_uuid()` as a primary key default on a high-insert table - UUIDv4 scatters inserts across the whole index, roughly doubling its size and its WAL volume
- Agent stores a UUID in a `text` column - 37 bytes instead of 16, and loses the type's operators
- Agent adds a surrogate `id` to a pure junction table - it permits duplicate pairs unless the unique constraint is added anyway
- Agent uses a natural key as the primary key for something the business can change - the change then cascades into every referencing table
- Agent adds a surrogate key and omits the `UNIQUE` on the business identifier - duplicates enter silently
- Agent does not index a foreign key column - deleting a parent row scans the entire child table while holding a lock
- Agent tries to eliminate gaps in a sequence - gaps are inherent and correct; a gapless counter is a separate serialised mechanism
- Agent uses `GENERATED BY DEFAULT` without needing it - `ALWAYS` catches the application supplying its own ids by mistake
- Agent puts the wrong column first in a composite key - the key's index follows the leftmost-prefix rule
