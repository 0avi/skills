# Persistence Slice Testing

Test the persistence layer with a slice - not the full context - backed by a **real** database via Testcontainers, never in-memory H2.

## The H2 trap

Every persistence slice (`@DataJpaTest`, `@JdbcTest`, `@DataJdbcTest`, `@JooqTest`) auto-configures an **embedded H2 DataSource by default**. Simple derived queries pass on H2, so the suite looks green - while anything database-specific silently diverges:

- A PostgreSQL native query using `to_tsvector`, `ON CONFLICT`, array or JSON columns, or a sequence fails against production with `Function "TO_TSVECTOR" not found` - after the H2 test passed.
- Type coercion, `NULL` ordering, string comparison and date arithmetic all differ.
- **Your Flyway migrations do not run**, because they are written in PostgreSQL dialect ([flyway.md](flyway.md)). So the H2 schema is generated by Hibernate, not by your actual migrations - the two can drift indefinitely without a single failing test.

That last point is the decisive one. Testing against the deployed database is the only way a persistence test means anything.

**The rule for all four slices:** add `@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)` so the DataSource is not swapped for H2, and supply a Testcontainers database. See [testcontainers.md](testcontainers.md).

## `@DataJpaTest`

```java
@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Import(TestcontainersConfig.class)
class OrderRepositoryTest {

    @Autowired OrderRepository orderRepository;
    @Autowired TestEntityManager entityManager;

    @Test
    void findsRecentOrdersByStatus() {
        orderRepository.saveAll(List.of(placedOrder(), shippedOrder(), placedOrder()));
        entityManager.flush();
        entityManager.clear();          // force a real read, not the first-level cache

        var found = orderRepository.findRecentByStatus(OrderStatus.PLACED, Limit.of(10));

        assertThat(found).hasSize(2);
    }
}
```

Import a **shared** container configuration so one container serves the whole suite and the context stays cacheable ([testing-strategy.md](testing-strategy.md)).

`entityManager.flush()` then `clear()` matters more than it looks. Without it, `findAll` can be served from the first-level cache and the test passes without ever issuing the SQL you meant to exercise.

Slices are `@Transactional` and roll back after each test. `@Sql("/test-data.sql")` is available for setup.

### What to test - and what not to

**Test:** custom `@Query` (JPQL and native), database-specific features, complex derived queries with edge cases, custom repository implementations, `@EntityGraph` fetch behaviour, constraint violations, and optimistic locking.

**Do not test:** `findById`, `save`, basic CRUD, or simple derived queries. That is Spring Data's code, and it has its own tests. A repository test suite that is mostly `save` and `findById` assertions is pure cost.

```java
@Test
void enforcesUniqueReference() {
    orderRepository.saveAndFlush(orderWithReference("ORD-1"));

    assertThatThrownBy(() -> orderRepository.saveAndFlush(orderWithReference("ORD-1")))
            .isInstanceOf(DataIntegrityViolationException.class);
}
```

`saveAndFlush` is required - a plain `save` defers the INSERT to commit, which happens after the test method returns, so the exception is thrown where no assertion can see it.

### Catching N+1

Query counts are the only reliable way; an N+1 is invisible in a passing functional test.

```java
@Test
void loadsItemsInOneQuery() {
    var statistics = entityManager.getEntityManager()
            .unwrap(Session.class).getSessionFactory().getStatistics();
    statistics.clear();

    var order = orderRepository.findWithItemsById(orderId).orElseThrow();
    assertThat(order.items()).hasSize(3);

    assertThat(statistics.getPrepareStatementCount()).isEqualTo(1);
}
```

Needs `spring.jpa.properties.hibernate.generate_statistics=true` in the test profile. Worth it on the read paths that matter - see [spring-data-jpa.md](spring-data-jpa.md).

## `@JdbcTest` - `JdbcClient` and `JdbcTemplate`

Auto-configures a DataSource plus both clients. Same `replace = NONE` plus Testcontainers rule.

```java
@JdbcTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Import(TestcontainersConfig.class)
class OrderSummaryQueryTest {

    @Autowired JdbcClient jdbcClient;

    @Test
    void aggregatesByStatus() {
        jdbcClient.sql("insert into orders (id, status, total_amount) values (?, ?, ?)")
                .params(UUID.randomUUID(), "PLACED", new BigDecimal("10.00")).update();

        var count = jdbcClient.sql("select count(*) from orders where status = :status")
                .param("status", "PLACED")
                .query(Long.class).single();

        assertThat(count).isEqualTo(1);
    }
}
```

## `@DataJdbcTest` and `@JooqTest`

Same rule for Spring Data JDBC repositories and for jOOQ's `DSLContext`. jOOQ against H2 masks dialect-specific SQL just as thoroughly as JPA does.

## Migrations are covered for free

With the real database and `spring.jpa.hibernate.ddl-auto=validate`, a persistence slice that **starts** has already proved that your Flyway migrations apply cleanly and that the resulting schema matches your entity mappings. That is a substantial amount of coverage from a configuration setting.

For a destructive or data-transforming migration, test the data explicitly: seed the old shape, migrate, assert the new one.

## If on Boot 3.5.x

Slice annotations, `@AutoConfigureTestDatabase`, `@ServiceConnection`, `JdbcClient` and `TestEntityManager` are identical. Two differences:

- **Testcontainers coordinates**: 1.x on 3.5.x versus 2.x on 4.x - see [testcontainers.md](testcontainers.md).
- **jOOQ**: the managed major version differs between the two BOMs; check `spring-boot-dependencies` rather than pinning it yourself.

## Gotchas

- Agent uses the default H2 for a persistence slice - dialect-specific SQL diverges silently, and your Flyway migrations never run
- Agent omits `@AutoConfigureTestDatabase(replace = NONE)` - the DataSource is swapped for H2 even with a container present
- Agent starts a container per test class - import a shared configuration
- Agent asserts on `findById` and `save` - that is Spring Data's code
- Agent omits `flush()`/`clear()` - the read is served from the first-level cache and the SQL is never exercised
- Agent uses `save` when testing a constraint violation - use `saveAndFlush`; a plain `save` defers the INSERT past the assertion
- Agent tests N+1 behaviour functionally - assert the query count
- Agent leaves `ddl-auto` at `update` in tests - Hibernate generates the schema, so migration drift is invisible; use `validate`
- Agent uses `@MockBean` for a repository in a persistence slice - the point is the real database
