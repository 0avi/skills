# Provenance and Signing

An SBOM says what is *inside* an artifact. Provenance says **where it came from**: which source commit, which builder, which workflow, on which platform. Signing makes both statements unforgeable. Together they answer the question a supply-chain attack depends on you being unable to answer, which is "is this the artifact our pipeline built, from our source?"

| Question | Answer |
| -------- | ------ |
| What is the minimum worth doing? | **Generate provenance in CI and verify it before deploying.** Generating without verifying is theatre |
| Where does verification belong? | **At the deployment gate**, not at the end of the build. A build verifying its own output proves nothing |
| Do I need a key? | **No.** Keyless signing through OIDC is the default now, and removes the key you would otherwise have to protect |
| What standard? | **SLSA** for build provenance levels, **in-toto** for the attestation envelope, **Sigstore** for the signing infrastructure |
| Is a signature enough? | No. A signature proves *who*; provenance proves *how*. An attacker with a valid key signs malware happily |

---

## The three layers, and why they are confused

Most confusion here is a layering error. From the bottom up:

| Layer | What it is | Example |
| ----- | ---------- | ------- |
| **Sigstore** | The signing and transparency infrastructure - certificates from OIDC identity, and a public append-only log | `cosign`, Fulcio, Rekor |
| **in-toto** | The *unopinionated* attestation format. A signed statement of the shape "this predicate is true about this artifact digest" | in-toto Statement, DSSE envelope |
| **SLSA** | The *opinionated* layer on top, specifying which fields provenance must carry to claim a given Build Level | SLSA Provenance predicate |

And alongside them:

| Framework | Role |
| --------- | ---- |
| **NIST SSDF (SP 800-218)** | States the *goals* an organisation must meet. What an auditor cites |
| **SLSA** | States *how* to meet the build-integrity subset of those goals |

That division is the useful one: **SSDF tells you the endpoint, SLSA tells you the steps.** If someone asks "are we SSDF compliant", the honest answer references controls; if they ask "what level is our build", that is SLSA.

## SLSA build levels

SLSA is at **v1.1** (approved April 2025), with v1.2 work in progress. The Build track is the part that concerns a pipeline:

| Level | Requirement, in practice |
| ----- | ------------------------ |
| **Build L1** | Provenance exists and is available. It may be self-reported and unsigned |
| **Build L2** | Provenance is **signed** and generated by a hosted build service, so it cannot be forged by the person requesting the build |
| **Build L3** | The build runs in an **isolated, ephemeral environment** and provenance is generated by the platform in a way the build itself cannot tamper with |

The jump from L2 to L3 is about *who could have lied*. At L2 the build service vouches for the provenance. At L3 the build's own code cannot influence what the provenance says, because generation happens outside the build's reach.

### GitHub Artifact Attestations

GitHub's documentation states that Artifact Attestations provide **SLSA v1.0 Build Level 2** on their own, and **Build Level 3** when the build runs through a **reusable workflow**. The reusable workflow is what supplies the isolation: the caller cannot alter the trusted build steps.

**Note the version skew, because it will confuse anyone reconciling the two documents:** GitHub describes levels against **SLSA v1.0**, while the current specification is **v1.1**. The Build-track level definitions are compatible, but the version numbers do not match, and a reader checking GitHub's claim against slsa.dev will find a different specification version. State which you mean.

```yaml
# minimum viable provenance on GitHub Actions
permissions:
  id-token: write        # required: signs via OIDC
  attestations: write    # required: writes the attestation
  contents: read
steps:
  - uses: actions/attest-build-provenance@<sha>
    with:
      subject-path: 'target/*.jar'
```

Attestations are signed through Sigstore. For public repositories a copy is written to the **Sigstore public-good transparency log**, which is publicly readable and immutable; a copy is also retained by GitHub. Once published for a given artifact an attestation **cannot be overwritten** with a different one for the same artifact. Verification does not require internet access.

*Cited from GitHub's documentation, not measured - it needs a hosted runner.*

## cosign, and the v3 changes that break older snippets

**Verified locally with cosign v3.1.3.** This matters because almost every `cosign` recipe published before v3 now fails, and the failure messages are misleading.

Working offline sign and verify, with a control:

```bash
export COSIGN_PASSWORD=""
cosign generate-key-pair

# strip the transparency log out of the signing config for an air-gapped flow
curl -sSL https://raw.githubusercontent.com/sigstore/root-signing/refs/heads/main/targets/signing_config.v0.2.json \
  | jq 'del(.rekorTlogUrls)' > sc-notlog.json

cosign sign-blob --key cosign.key --yes \
  --signing-config sc-notlog.json --new-bundle-format \
  --bundle demo.bundle target/app.jar

cosign verify-blob --key cosign.pub \
  --bundle demo.bundle --new-bundle-format \
  --insecure-ignore-tlog=true target/app.jar
```

Measured results:

| Input | Result |
| ----- | ------ |
| The genuine artifact | **`Verified OK`** |
| The same artifact with one byte appended | **Fails**: `invalid signature when validating ASN.1 encoded signature` |

The negative control is the point. A verification step that has never been shown to *fail* on a tampered artifact has not been tested.

**The same control, run against a real registry rather than a file.** Two images pushed to one tag, then the *second* digest signed:

| Verification target | `cosign verify` exit code |
| ------------------- | ------------------------- |
| The digest that was signed | **0** |
| The other digest in the same repository | **10** |

A signature is bound to a digest, not to a repository or a tag. Verifying "the image at `:prod`" proves nothing unless you resolve and check the digest you actually signed.

**Three v3 traps, all hit while getting the above to work:**

1. **`cosign sign-blob --key ... --tlog-upload=false` alone no longer works.** It errors with `must specify --bundle with --new-bundle-format`. The v2-era one-liner is dead.
2. **`--tlog-upload=false` is mutually exclusive with `--signing-config`** - and cosign's own error message tells you to combine them, recommending you pass a signing config *and* the flag. Doing exactly what the message says produces another error. Drop the flag and let the tlog-less signing config do the work. **This is a defect in the error message, verified by experiment.**
3. **Verification contacts Rekor by default.** Without `--insecure-ignore-tlog=true` an offline verify fails against the public log with `searching log query ... 400`, which reads like a signature problem and is not.

For an air-gapped or on-premises pipeline, budget real time for this. The keyless public-good path is much smoother than the offline key-based path.

## Keyless signing, and why to prefer it

Keyless signing exchanges the CI platform's OIDC token for a short-lived certificate binding the signature to a *workflow identity* rather than to a key someone holds:

```bash
# in CI, with id-token: write - no key material anywhere
cosign sign-blob --yes --bundle app.bundle target/app.jar
```

Verification then asserts the identity, which is the useful part:

```bash
cosign verify-blob --bundle app.bundle \
  --certificate-identity-regexp 'https://github.com/myorg/myrepo/.github/workflows/release.yml@.*' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  target/app.jar
```

**Verify the identity, not merely the signature.** `cosign verify` without identity constraints accepts anything signed by anyone with a Sigstore certificate, which is everyone. Omitting `--certificate-identity-regexp` is the most common way a signing pipeline provides no security at all.

## Verify at the deployment gate

The whole scheme collapses if verification happens in the build. Place it where the artifact is *consumed*:

| Target | Where verification belongs |
| ------ | -------------------------- |
| Kubernetes | An admission controller - Sigstore Policy Controller, Kyverno or Gatekeeper - rejecting unsigned or unattested images |
| ECS, App Service, Container Apps | A deploy-stage step that verifies the digest before the service is updated |
| VM or on-prem | The install script, before unpacking |
| Cloudflare Workers | No image to verify; verify the built bundle before `wrangler versions upload`. See [target-cloudflare-workers.md](target-cloudflare-workers.md) |

## Version notes

| | Status |
| --- | ------ |
| SLSA specification | **v1.1**, approved April 2025; v1.2 in progress |
| GitHub Artifact Attestations | Documented against **SLSA v1.0**: Build L2, or L3 via reusable workflows |
| cosign | **v3.1.3** verified here. v3 changed the offline CLI incompatibly |
| in-toto | The attestation vehicle SLSA recommends |
| NIST SSDF | **SP 800-218 v1.1** |

- **Any `cosign` snippet from before v3 should be assumed broken.** Test it rather than trusting it.
- **SLSA level claims must name the specification version.** "SLSA L3" without a version is ambiguous now that GitHub and slsa.dev cite different ones.
- **Not verified here:** GitHub Artifact Attestations end-to-end, keyless signing, and admission-controller enforcement. All need a hosted runner or a cluster.

## Gotchas

- Agent signs in CI and never verifies anywhere - generating provenance without a verification gate is theatre, and costs build minutes for nothing
- Agent verifies in the same job that built the artifact - proves nothing; the build could have produced both the artifact and its attestation
- Agent runs `cosign verify` without `--certificate-identity-regexp` - accepts a signature from **any** Sigstore identity, which is no control at all
- Agent copies a pre-v3 `cosign sign-blob --tlog-upload=false` line - **verified to fail** on v3.1.3 with a `--new-bundle-format` error
- Agent follows cosign's own error message and passes `--signing-config` together with `--tlog-upload=false` - **verified to fail**; the message is wrong, drop the flag
- Agent debugs an offline verify failure as a signature problem - a Rekor lookup failure (`searching log query ... 400`) looks identical; add `--insecure-ignore-tlog=true`
- Agent claims SLSA L3 because provenance is signed - L3 additionally requires the build to be unable to influence its own provenance, which on GitHub means a reusable workflow
- Agent conflates SBOM with provenance - one is contents, the other is origin; an auditor asks for both and they are different documents
- Agent asserts a signature proves the artifact is safe - it proves who signed it. Provenance proves how it was built. Neither proves the code is good
- Agent never tests the negative case - a verification step that has not been shown to reject a tampered artifact is unverified
